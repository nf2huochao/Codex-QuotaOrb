# Codex 状态同步与无闪烁设计

## 目标

让圆球、三段胶囊和详情页在 Codex 状态变化时及时同步，同时保持界面稳定，不因数据刷新而闪烁、重建或重复缩放窗口。

目标时效：任务变化通常 1～2 秒内反映；额度和 Token 在 10～30 秒内校验；120 秒全量轮询作为最终兜底。数据源不可用或过期时明确标记，不把旧数据当成最新状态。

## 当前问题

1. 前端收到 `snapshot-updated` 后会重新生成当前界面的 `innerHTML`，数据没有变化的区域也会重新进入动画。
2. 刷新流程同时触发 loading render、数据 render 和窗口尺寸计算，多个异步结果可能互相覆盖。
3. 后端主要依赖 120 秒轮询；任务、额度和 Token 没有区分同步频率，也没有按字段判断是否真的变化。
4. 当前应用启动的是独立 app-server，不能假定一定能接收到 Codex 桌面进程的实时事件，因此需要本地任务记录作为任务变化的可靠补充。

## 方案

采用“本地任务监听 + 额度/Token 差量轮询 + 前端局部更新”的同步中枢。

### 后端同步中枢

- 任务监听器每秒检查 Codex 本地状态数据库中的线程更新时间，并检查对应 rollout 文件的修改时间。
- 任务状态映射为：等待回复/授权、执行中、已完成、无活跃任务；只在任务集合或状态真正变化时发布任务差量。
- 额度和 Token 校验器每 15 秒请求 `account/rateLimits/read` 与 `account/usage/read`，将结果与上一次快照做字段比较；额度百分比、重置时间、套餐、重置机会、Token 数值或数据日期变化时才发布差量。
- 每 120 秒执行一次完整快照校验，修复监听器遗漏、文件变化延迟或短暂请求失败造成的偏差。
- 事件统一包含 `source`、`fetchedAt`、`changedAt` 和 `schemaVersion`。局部更新失败时保留上一份已验证数据，但将状态改为过期或错误。

### 前端更新策略

- 三个界面的根节点和主要 DOM 结构只在界面切换时创建；数据事件只更新已有节点的文字、颜色、进度环和状态灯。
- 数据事件不触发 `surface-in` 动画，不触发原生窗口尺寸变化；只有圆球、胶囊、详情页切换才调整窗口尺寸。
- 同一批次内 150ms 的连续数据变化合并处理，避免任务状态连续变化造成快速抖动。
- 进度环只在百分比改变时做短过渡；任务状态灯只在状态改变时切换颜色；Token 数值直接更新，不重建容器。
- 更新按钮只反映请求状态，不再通过整页 loading 重绘造成闪烁。

### 状态优先级

任务状态灯保持：需要回复/授权（红） > 有任务完成（绿） > 正在执行（黄） > 无活跃任务（灰）。任何一个未确认的完成任务出现后立即显示绿色。

## 错误与降级

- 额度或 Token 请求失败：显示最近一次成功数据，同时标记“数据过期/读取失败”，不更新时间戳。
- 任务监听暂时失败：继续使用 120 秒全量校验，并在详情页显示同步来源和最近成功时间。
- 本地文件无法读取：任务状态显示为未知，不推断为完成或执行中。
- 更新事件乱序：使用 `changedAt` 丢弃更旧事件，避免旧数据覆盖新数据。

## 验收标准

- 在任务新增、状态变化、完成确认时，圆球和胶囊的状态灯与任务文字在 2 秒内同步。
- 额度或 Token 变化后，在下一次 15 秒校验内同步；未变化时界面不发生闪烁。
- 连续刷新 20 次，当前界面不重新播放进入动画，窗口尺寸不重复变化。
- 三态双击循环仍为：圆球 → 三段胶囊 → 详情页 → 圆球。
- 读取失败、数据过期、数据日期变化均能被用户明确识别。
- 前端单元测试覆盖差量更新与状态优先级；Rust 测试覆盖任务变化检测、字段比较、乱序事件和错误降级；浏览器测试覆盖三态切换及连续更新稳定性。

## 非目标

- 不修改 Codex 桌面应用本身。
- 不承诺额度服务端提供绝对实时推送；额度和 Token 以可控频率轮询为准。
- 不在本阶段增加新的移动端同步协议或远程云端服务。
