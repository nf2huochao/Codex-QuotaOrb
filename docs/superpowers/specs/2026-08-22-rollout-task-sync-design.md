# Rollout 任务同步设计

## 目标

让桌面球、三等分长条、详情页和网页端使用同一份任务状态：任务发现以 Codex Rollout 日志为主，额度与用量继续由 app-server 提供，批准请求保留手动批准/拒绝。

## 方案

在 Rust 端增加只读的 Rollout 任务观察器。观察器扫描 `~/.codex/sessions/YYYY/MM/DD/*.jsonl` 的近期文件，按文件偏移量增量读取新增行；从 `session_meta`、用户消息、工具调用、审批请求、完成事件和 token 事件提取会话 ID、首句任务标题、状态、等待原因与 Token。扫描结果与 app-server 的 `thread/list` 按会话 ID合并：Rollout 提供任务发现和实时状态，thread/list 补充线程路径/更新时间，事件流中的批准请求优先级最高。

状态合并规则：

- `needs_action` 优先于 `running`，保留等待原因和批准请求 ID；
- `running` 只在最近有活动时保留；
- `completed` 保留一段时间供验收，直到用户点击“可验收”；
- 没有活动的会话不计入长条数量；
- 所有界面从 `SnapshotStore` 的同一快照读取，长条只显示颜色点与数量，详情显示完整任务列表。

## 批准请求

继续使用 app-server 的 JSON-RPC 批准请求响应，不自动批准。Rollout 中只能作为红色状态的发现/兜底来源；只有拿到当前 app-server 的请求 ID 才显示可操作的“批准/拒绝”按钮，避免误操作或伪造授权。

## 失败与降级

Rollout 目录不可读时继续使用 app-server 线程列表；日志解析失败只跳过当前行；数据源暂时中断时保留最近有效快照并明确显示断线状态，不把旧数据标为最新。

## 验证

覆盖多文件并行任务、首句标题过滤、批准优先级、完成可验收、日志截断/追加、长条与详情计数一致，以及现有 Rust、前端和 UI 测试。
