# 事件流主导的任务状态同步设计

## 目标

消除日志内容导致的误判，并保证圆球、长条和详情页使用同一份任务状态：只有当前仍未解决的 app-server 请求才能显示红色；实时执行任务稳定显示黄色；完成事件显示绿色；没有活动时显示灰色。

## 状态规则

- 红色 `needs_action`：仅由 app-server 的结构化 server request 产生，必须同时具备当前任务关联关系和未解决的 request id。请求收到 `serverRequest/resolved`、拒绝、批准或完成事件后立即清除红色。
- 黄色 `running`：由 app-server 的 turn/item 运行事件产生；重连或事件漏报时，可由 `thread/list` 中明确的 `active`/`running` 状态补回。`thread/list` 不能生成红色。
- 绿色 `completed`：由显式完成事件产生，并保留到用户验收；轮询不能把较新的绿色覆盖回黄色。
- 灰色 `none`：任务没有活动状态，或没有可确认的实时状态。
- 阻塞提醒：只作为黄色任务的附加字段，不改变黄色状态，也不产生红色批准语义。

## 数据流

1. `CodexClient` 接收 app-server JSON-RPC 消息，维护未解决批准请求表，并广播结构化事件。
2. `TaskRegistry` 是唯一状态归并层，按稳定的 thread id 合并事件、活动线程补偿和显式完成/解决事件。
3. `thread/list` 只提供活动任务补偿；日志观察器不再参与状态归并，只保留标题、当前内容和 token 等展示字段。
4. 三个 UI 表面只消费 `Snapshot.tasks` 和 `Snapshot.task_counts`，禁止自行读取或推断任务状态。

## 重连与错误处理

连接恢复后先读取活动线程并合并为黄色，再等待后续 app-server 事件；没有有效 request id 的等待字样不得变红。连接断开时保留最近一次有效任务状态，同时显示连接错误，不将旧日志内容当成新状态。

## 验证标准

- 历史 rollout 中包含 `request_user_input` 或“需要批准”等文字，但没有未解决 request id 时，任务不能变红。
- 两个或多个 active/running 线程在长条和详情页显示完全相同的数量。
- 事件流暂时漏掉某个任务时，`thread/list` 能补回黄色任务；补偿数据不能生成红色。
- 解决批准请求后，红色任务立即恢复为黄色或绿色；阻塞提醒不会改变基础颜色。
- Rust、前端单元测试和生产构建全部通过。
