# Codex 任务统一快照与小时额度趋势设计

## 背景

当前任务状态来自 app-server 实时事件、任务轮询、完整轮询和 rollout 日志扫描。四条路径分别修改任务列表，导致长条、详情页和网页端在不同时间收到不同的任务集合；任务轮询还可能用不完整的 `thread/list` 结果覆盖事件中已经发现的任务。批准请求没有稳定绑定到对话任务时，红色状态和批准/拒绝按钮会消失。历史趋势则按刷新次数采样，前端只取最近 12 点并同时绘制 Token，无法表示当天 24 小时的额度变化。

## 目标与验收标准

- 长条、详情页、局域网网页端在同一快照版本中显示相同的红/黄/绿/灰状态数量；不再出现长条显示 1 个而详情显示多个的情况。
- app-server 的命令、文件修改、权限和用户输入批准请求均能按 `threadId` 关联到对应对话，显示红色状态、等待原因、批准和拒绝按钮；未批准前不自动放行。
- 收到批准响应、拒绝、`serverRequest/resolved` 或对应 `item/completed` 后，红色请求只结束对应任务，不影响同一对话中的其他任务。
- Codex 注入的 `<recommended_plugins>`、环境上下文和协议标记不再被显示为标题或当前内容；标题保持对话标题，当前进行内容单独显示。
- 详情趋势显示当天 24 个整点槽位，只使用额度百分比；没有采样的小时保留空槽，不用旧数据伪装成新数据；趋势区域不再显示 Token 曲线或 Token 趋势摘要。
- 既有配对、刷新、三界面双击循环、桌面与网页配色和布局逻辑保持不变。

## 方案

### 1. 统一任务注册表

在后端维护一份以稳定对话 ID 为主键的任务注册表。稳定 ID 的优先级为 `threadId`，其次是已知 session ID；`turnId`、`itemId` 和批准 request ID 只作为当前任务或请求的关联字段，不得再单独生成一条伪任务。每次事件、轮询或 rollout 扫描先合并进注册表，再由注册表生成完整 `Snapshot`。

合并规则：

- 事件状态优先级为“需要处理 > 正在执行 > 已完成 > 无活跃任务”；同一任务的红色状态在收到对应解决/完成事件前不能被普通 `thread/list` 的 active 或 idle 覆盖。
- 轮询只能补充或确认任务，不能删除最近仍在运行、等待批准或可验收的事件任务；任务过期由统一的可见时间窗口处理。
- rollout 只补充标题下的当前内容、等待原因和 token 计数，不改变已经明确的对话标题，也不创建 `<recommended_plugins>` 等上下文任务。
- 每次发布都重新按未确认任务计算 `needs_action`、`running`、`completed` 和 `none` 四类统计，并写入快照；三个前端只读这份快照，不自行根据不同来源重算任务集合。

### 2. 实时事件与批准关联

Codex app-server 的 server-initiated JSON-RPC 请求按以下字段解析：`method`、请求 `id`、`params.threadId`、`params.turnId`、`params.itemId`、`params.reason`。支持至少：

- `item/commandExecution/requestApproval`
- `item/fileChange/requestApproval`
- `item/permissions/requestApproval`
- `item/tool/requestUserInput`
- `mcpServer/elicitation/request`

收到请求时，将批准 request ID 和完整关联字段写入对应对话任务，状态设为 `needs_action`，等待原因使用 `reason` 或请求类型生成。批准接口只允许明确的批准或拒绝；成功写回 app-server 后，等待 `serverRequest/resolved` 或最终 `item/completed`，再清理批准字段并更新状态。对于 Hook 输入，解析采用可选字段和 snake/camel 两种命名，兼容包装对象，不能因缺少非关键字段直接丢弃请求。

### 3. 前端渲染契约

后端快照增加稳定的任务状态统计字段，至少包含四类数量和快照版本。桌面长条、详情页和网页长条均使用该统计字段；详情列表使用同一快照中的任务数组。长条只显示有工作的颜色点和数量，没有任务时显示灰点，不显示“活跃任务/已完成”等另一套计数文案。

详情任务行保持“对话标题 → 当前进行内容 → 状态”的层次。绿色任务继续显示“可验收”按钮；红色任务在等待原因下显示“批准”和“拒绝”，按钮只调用对应 request ID。

### 4. 当天 24 小时额度趋势

`UsagePoint` 只保留整点时间和额度百分比。后端以本地当天的小时桶去重，同一小时只保留最后一次成功额度；只保留当天 24 个桶，跨日自动清空上一天。前端固定渲染 24 个位置，缺失小时显示空槽，标题显示“当天额度变化 · 24 小时”。Token 卡片仍可在详情顶部显示当日 Token 总量，但趋势卡不再出现 Token 文案、曲线或摘要。

## 数据流

```text
app-server request/notification ─┐
thread/list / rate limits ───────┼─> 统一任务注册表 + 小窗口合并 ─> SnapshotStore ─> Tauri/WebSocket ─> 三种界面
rollout JSONL watcher ───────────┘                                      │
                                                                         └─> 当天整点额度历史
```

事件进入后在一个短合并窗口内收集同一批关联更新，只发布一次完整快照，避免界面先收到“只有一个任务”的中间状态。快照的 `changed_at` 单调递增，客户端继续丢弃旧版本。

## 错误与降级

- app-server 断开时保留最后成功快照并显示断线状态；不把旧任务标记为新完成。
- 批准请求字段缺失时保留原始 request ID 和可读原因，任务显示红色但按钮只在后端确认仍可响应时启用。
- 某小时没有成功额度读取时显示空槽；读取失败不能复制上一小时数值。
- 同一任务收到重复事件时按 request ID、item ID 和更新时间去重，重复事件不增加数量。

## 测试范围

- Rust 协议测试：四种批准请求的字段解析、snake/camel 兼容、thread/turn/item/request 关联、解决事件清理。
- Rust 合并测试：不完整轮询不能删除事件任务；红色优先级保持；重复事件和重复 rollout 不增加任务；快照四类统计与任务数组一致。
- Rust 历史测试：同一小时折叠、跨日重置、最多 24 桶、缺失小时不补旧值。
- TypeScript 测试：长条和详情使用同一统计字段；标题/当前内容分层；红黄绿灰渲染；趋势不包含 Token 轨道。
- Playwright 测试：三界面循环切换、同一快照下长条与详情数量一致、红色批准/拒绝按钮存在、网页端初始和 WebSocket 更新一致。

## 不在本次范围

- 不改变远程访问方式、配对码流程、安装包签名和发布流程。
- 不自动批准任何 Codex 请求。
- 不重做既有奶油白、鼠尾草绿和杏色视觉设计。
